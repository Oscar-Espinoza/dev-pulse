# 10 — Auth & users

Files: `app/dependencies.py` (47 lines), `app/routers/users.py` (35 lines).

Authentication in this app is a random string in a header. This chapter is about why that
was chosen — twice — and about the FastAPI mechanism that makes it invisible in every route.

## The decision, made twice

> 🔑 **Decision: API-key authentication. No JWT, no passwords, no OAuth2.** Recorded in the
> original build plan as *"API-key auth … No JWT/passwords."*

Then, months later, the same question came back as a feature request: add JWT with OAuth2
password flow, `python-jose`, `passlib`/`bcrypt`. It was planned in detail — and rejected
before implementation with a one-line answer: *"Actually leave the authentication as it
is."* The stats-endpoint plan records the reversal and turns it into a constraint: *"Do not
modify `app/dependencies.py`, the `X-API-Key` scheme, or any existing auth test."*

The reasoning is worth internalizing, because it generalizes past this codebase. JWT is a
*more capable* authentication scheme. It is not a *better* one for this app. What would it
add here?

- **Expiring credentials?** Useful — but the app has no way for a user to rotate a key
  anyway, so it swaps one gap for another.
- **Stateless verification?** Its main advantage: no database lookup per request. But this
  app hits the database on every request regardless, to load the user.
- **Standard client tooling?** The clients are `curl` and a scheduler. A header is simpler.

Against that: password hashing, token issuance, expiry handling, refresh tokens, two new
dependencies, and a security surface where mistakes are subtle and expensive. For a
single-purpose API whose clients are scripts, the API key is not the lazy choice — it's the
proportionate one.

The lesson isn't "API keys are good." It's that "more sophisticated" and "more appropriate"
are different axes, and adding capability you don't need is a cost you pay forever.

## Registration: the key exists for exactly one moment

```python
@router.post("", response_model=UserRead, status_code=status.HTTP_201_CREATED)
async def create_user(payload: UserCreate, session: DbSession) -> User:
    """Register a user and return their generated API key.

    The key is only shown here — store it; all monitor endpoints require it
    in the ``X-API-Key`` header.
    """
```
`app/routers/users.py:16-22`

The key is generated by the model layer, not the route:

```python
def generate_api_key() -> str:
    return secrets.token_urlsafe(32)
```
`app/models.py:36-38`, wired in as `default=generate_api_key` at `:54-56`.

> 🐍 **Python note:** `secrets` is the standard library's *cryptographically secure*
> random module. The similarly-named `random` is not — it's seeded predictably and is
> unsafe for anything security-related. `token_urlsafe(32)` gives 32 random bytes encoded
> as URL-safe text: roughly 43 characters, not guessable.

Because the default lives on the column, a key is generated for any `User` created anywhere
— routes, tests, future admin tooling — with no way to forget it.

`UserRead` includes `api_key` (`app/schemas.py:90`), which is why registration returns it.
No other endpoint does. There's no "show me my key" route: lose it and you make a new
account. That's a deliberate simplification, and one of the things chapter 15 lists as a
production gap.

## Duplicate email → 409

```python
existing = await session.execute(select(User).where(User.email == payload.email))
if existing.scalar_one_or_none() is not None:
    raise HTTPException(status_code=status.HTTP_409_CONFLICT, detail="A user with this email already exists")
```
`app/routers/users.py:23-28`

> 🔑 **Decision: registering an existing email is a 409 Conflict, not a silent re-issue of
> the key.**

Consider the alternative: "email already exists, so here's your key again." That turns
`POST /users` into a credential-retrieval endpoint that anyone who knows your email address
can call. The 409 is the boring answer and the correct one.

Note there's *also* a unique index on the column (`app/models.py:53`). The check is for a
clean error message; the index is the actual guarantee. Two clients registering the same
email simultaneously will both pass the check, and the database will reject the loser — the
right layering, even though the resulting error is uglier.

## The dependency: auth as a type annotation

```python
api_key_header = APIKeyHeader(name="X-API-Key", auto_error=False,
                              description="API key issued by POST /users")

async def get_current_user(session: DbSession,
                           api_key: Annotated[str | None, Security(api_key_header)]) -> User:
    if api_key is None:
        raise HTTPException(401, detail="Missing X-API-Key header")
    result = await session.execute(select(User).where(User.api_key == api_key))
    user = result.scalar_one_or_none()
    if user is None:
        raise HTTPException(401, detail="Invalid API key")
    return user

CurrentUser = Annotated[User, Depends(get_current_user)]
```
`app/dependencies.py:13-45`, condensed.

> 🔑 **Decision: `auto_error=False`.** With the default `True`, FastAPI raises its own
> generic 403 when the header is absent and this function never runs. Setting it `False`
> makes the parameter `None` instead, so the app controls the response — a 401 (not 403,
> which means "authenticated but not allowed") with a message that distinguishes *missing*
> from *invalid*.

That distinction is a genuine developer-experience choice. "Missing X-API-Key header" tells
an integrator they forgot the header; "Invalid API key" tells them they used the wrong
value. A single generic error makes them guess.

Then the payoff line:

```python
CurrentUser = Annotated[User, Depends(get_current_user)]
```
`:45`

Every protected route now reads:

```python
async def list_monitors(user: CurrentUser, session: DbSession) -> list[Monitor]:
```

> ⚙️ **FastAPI note:** This is dependency injection doing real work.
> `get_current_user` runs *before* the route body. If it raises, the body never executes.
> So **a route that declares `user: CurrentUser` is authenticated by construction** — there
> is no `if not authenticated: return 401` anywhere in this codebase, and no way to forget
> one.

Compare with middleware, the other common approach: middleware runs on every request and
needs a list of exempt paths, which is a list you can get wrong. Here, protection is opt-in
per route and visible in its signature. `GET /healthz` (`app/main.py:69`) is public simply
because it doesn't ask for a user.

And because `get_current_user` itself depends on `DbSession`, the dependency graph resolves
recursively: request → session → user → route. FastAPI walks it in order and unwinds
correctly afterward.

## `get_scheduler`: injecting a live object

```python
def get_scheduler(request: Request) -> MonitorScheduler:
    """The process-wide MonitorScheduler created in the lifespan context."""
    return request.app.state.scheduler

SchedulerDep = Annotated[MonitorScheduler, Depends(get_scheduler)]
```
`app/dependencies.py:40-46`

Same pattern, different resource: reach into `app.state` (chapter 12) and hand the route
the running scheduler.

The reason this is a *dependency* rather than a module-level global is testability. Because
routes ask for `get_scheduler`, `tests/conftest.py:81` can substitute a `SchedulerSpy` that
records calls instead of scheduling anything. That single line is what lets chapter 13's
API tests assert "creating a monitor scheduled exactly one job with a 300-second interval"
without APScheduler being involved at all.
